# 第二轮优化方案：性能、边界与报错、稳定性（2026-10-20）

## 背景

第一轮（`docs/OPTIMIZATION_PLAN.md`）解决了主线程阻塞与代码结构问题。本轮对照“产线 7×24 小时无人值守运行”的要求重新审查全部代码，重点是：异常输入下会不会出错、出错后能不能被发现、长期运行会不会慢慢坏掉。

问题按影响分三级：

- **P0**：会导致数据错误或长期运行后停机，且没有任何告警。
- **P1**：明显的性能问题，或异常情况下行为不正确、报错不清楚。
- **P2**：提升故障发现与恢复能力。

第 7 节列出需要产品确认的取舍，确认后再动手。

## 1. P0：数据正确性与长期运行

### 1.1 归档清理会永久停滞，并且仍然报告成功（已复现）

**现象**：`ArchiveMaintenance::cleanup` 每轮取 500 组过期图片名。路径“不安全”的组（`imageName` 为绝对路径、带 `../`、为空或扩展名不是图片）会被跳过，但对应的数据库记录也不删除，下一轮又被选中。只要累计 500 组这样的记录，清理就再也不会前进。

**复现**（用项目中的真实 `ArchiveMaintenance` 代码）：先插入 500 条 `imageName` 为 `/data/cam/A_n.png` 或 `../cam/A_n.png` 的过期记录，再插入 1 条正常的过期记录：

```text
round 1: ok=1 removed=0 more=0 records_left=501 normal.png_exists=1
round 2: ok=1 removed=0 more=0 records_left=501 normal.png_exists=1
round 3: ok=1 removed=0 more=0 records_left=501 normal.png_exists=1
```

正常记录永远不会被清理，而返回值是“成功、没有更多”，日志中看不出任何异常。只要现场有一台客户端在 `imageName` 里发送完整路径，过一段时间清理就会停止，磁盘被慢慢写满。

**方案**：

1. 入库时校验 `imageName`（见 1.3 与决策 D1），从源头杜绝路径。
2. 清理遇到不安全路径时：只删除数据库记录、不删文件，记 WARN 日志并计数，保证每轮都有进展。
3. 返回“本轮选中数 / 删除记录数 / 删除文件数 / 跳过数”，跳过数大于 0 时在状态栏告警。

**验收**：上述复现用例中正常记录在第 1 轮被删除；新增回归测试。

### 1.2 没有磁盘空间保护

**现象**：清理只按保留天数删除，不看剩余空间；FTP 接收、数据库写入、日志写入都不检查磁盘。磁盘写满时三者同时失败，SQLite 可能留下不完整的 WAL，界面只看到零散的报错。

**方案**：

- 每分钟用 `QStorageInfo` 检查图像目录与数据库所在分区：
  - 剩余 < 10%：状态栏告警，写 WARN；
  - 剩余 < 5%：FTP 对新上传返回 `452 Insufficient storage`，并立即触发一次清理（按时间从旧到新，直到恢复到 10%，最少保留 7 天，见决策 D3）；
  - 剩余 < 2%：停止接收 TCP 入库并返回明确错误，避免写坏数据库。
- 系统设置页显示各分区剩余空间。

**验收**：用小容量回环文件系统（或可配置阈值）模拟磁盘满，确认依次触发告警、拒收与清理，恢复后自动继续接收。

### 1.3 记录关联的是“声明的图片名”，不是“实际落盘的文件”

数据库 `record.imagename` 保存的是 TCP 报文中的 `imageName`，历史查询和清理都用它去拼路径。实际落盘的文件可能和它对不上：

| 场景 | 实际落盘 | 结果 |
| :--- | :--- | :--- |
| 同名不同内容重传 | `x_v2.png` | 新记录仍显示旧图 `x.png`（**显示错误照片，无任何提示**）；`x_v2.png` 不被引用，永不清理 |
| 相机上传到子目录（FTP 支持 MKD/CWD） | `cam1/x.png` | 历史查询找不到图片；清理删不到文件 |
| 文件名大小写不同（匹配不区分大小写，Linux 文件系统区分） | `X.PNG` | 同上 |
| `imageName` 带路径 | 任意位置 | 界面可显示磁盘上任意图片（`resolveImagePath` 先直接检查原路径），并触发 1.1 |

**方案**：

1. `record` 表增加 `image_path` 列（相对图像根目录的实际文件路径），关联成功时写入：
   - 图片先到：TCP 入库时从待关联缓存取得实际路径，随记录一起写入；
   - 记录先到：FTP 落盘后执行 `UPDATE record SET image_path=? WHERE imagename=? COLLATE NOCASE AND image_path IS NULL`。
2. 待关联缓存按“客户端请求的文件名”建键，而不是按落盘后的文件名，`_v2` 版本能正确关联到新批次。
3. 历史查询、清理、监控图片优先使用 `image_path`，为空时才回退到旧逻辑（兼容历史数据）。
4. `resolveImagePath` 不再接受绝对路径和 `..`。

**验收**：分别覆盖上表四种场景的集成测试（FTP 先到 / TCP 先到各一次）。

### 1.4 `timestamp` 没有合理范围

**现象**：客户端时钟错误或误发一条 2099 年的数据后，它会永远排在“最新”：首页当前架号、监控状态、“最新架号”查询都卡在这条数据上，清理也永远不会删除它。

**方案**：拒收早于“当前时间 − 保留天数”或晚于“当前时间 + 10 分钟”的报文，返回明确的错误信息（窗口见决策 D2）。可选：服务端记录接收时间，与客户端时间偏差大于 1 分钟时告警，提示客户端校时。

## 2. P1：性能

### 2.1 统计详情页按原图解码缩略图

`RackWheelStats.qml`、`DriveWheelRackDetail.qml` 的列表缩略图没有设置 `sourceSize`，每张都按相机原图分辨率解码，一页最多 200 张。按 500 万像素估算，单张约 20 MB 内存，一页可达数 GB，打开页面会明显卡顿甚至内存耗尽。`AlertRecordPage.qml`、`CalibrationPage.qml` 的预览图同样未限制尺寸。

**方案**：缩略图统一设置 `sourceSize`（按显示尺寸的 2 倍）；`ZoomOverlay` 的大图（`sourceSize` 8192）改为 `cache: false`，避免单张占用数百 MB 的图片缓存。

**验收**：打开 200 条结果的统计详情页，进程内存增量 < 300 MB，首屏出现 < 1 秒。

### 2.2 结果被静默截断

上述三个统计详情页向 `searchPaged` 请求 1000 条，后端上限是 200 条，多余结果被丢弃，界面没有提示。

**方案**：改为分页加载（复用 `PageBar`），或至少在结果达到上限时显示“仅显示最新 200 条”。

### 2.3 主线程上仍有的重查询

| 位置 | 情况 |
| :--- | :--- |
| `gearSumQuery`（轮系统计页） | 按日期范围对全部架号分组统计，同步执行；与已测的架号统计同量级（180 天约 95 ms） |
| `WeeklyReport::generateForWeek` | 启动时与每周一在主线程扫描一周数据并写 CSV |

**方案**：`gearSumQuery` 并入 `requestStats` 异步接口；周报生成移到维护线程。

### 2.4 清理事务与主线程入库争用写锁（待测量）

清理在维护线程中一次处理 500 组图片名（每组删除两张表并触发触发器）。持有写锁期间，主线程上的 TCP 入库最多会等待 `busy_timeout`（5 秒），界面随之卡住。

**方案**：先在 50 万条记录的测试库上测量单批清理耗时；超过 50 ms 时把每批降到 100 组，或拆成多个小事务。

### 2.5 日志开销

- 每条 FTP 协议日志都要在主线程上打开、追加、关闭一次 `ftp.log`；12 路相机同时上传时每秒可达上百次。
- 同一事件重复记录：TCP 模块记一次，`AppController` 转发时再记一次（实际日志中“[TCP] 服务已启动”“客户端连接”均出现两次）。
- 发布版也以 trace 级别记录全部协议细节。

**方案**：`ftp.log` 改为常驻打开、定时刷新的写入器；删除重复的转发日志；日志级别可在系统配置中设置，发布版默认 INFO。

## 3. P1：边界与报错

### 3.1 TCP 接收

| 问题 | 方案 |
| :--- | :--- |
| 没有空闲超时，半开连接永久占用连接名额（上限 32） | 5 分钟无数据即断开，并开启 TCP keepalive |
| 单行上限 2 MB，而协议最大报文约 20 KB | 单行上限降到 64 KB |
| JSON 解析失败时把整行原始报文写进 WARN 日志 | 日志中截断到 256 字节 |
| 客户端只发不收时，回包在发送缓冲中无限积压 | 待发送数据超过 1 MB 时断开 |

### 3.2 网络访问控制

TCP 与 FTP 都监听所有网卡，没有来源限制；FTP 同一连接 5 次登录失败后断开，但可以立即重连继续尝试。

**方案**：FTP 按来源 IP 计数，10 分钟内失败 10 次封禁 15 分钟；可选的来源 IP 白名单（见决策 D4）。

### 3.3 FTP 被动模式端口随机

PASV/EPSV 监听随机端口，现场机器开启防火墙时上传会时好时坏。

**方案**：被动端口范围可配置（见决策 D5），并在 README 中写明需要放行的端口。

### 3.4 启动失败没有提示，服务异常不会自动恢复

- 数据库打不开或建表失败时直接 `return 1`，Linux 下无任何提示，Windows 下也没有弹窗。
- FTP / TCP 端口被占用导致启动失败后不会重试。

**方案**：启动失败显示原生错误框（含原因与日志路径）；FTP / TCP 监听失败后每 30 秒自动重试，并在状态栏显示。

### 3.5 图片校验不完整

`ImageIngest::validate` 只读取图片头（`size()` + `canRead()`），截断的文件也能通过。校验已在 FTP 线程执行，可以改为完整解码。

**方案**：完整解码校验；先测量 500 万像素 JPEG / PNG 的解码耗时，确认不影响 12 路并发上传。

### 3.6 状态栏告警时间只有日期

日志通知传给界面的时间字段用的是 `formatDate`，只有年月日，没有时分秒。

**方案**：改为完整时间。

## 4. P2：稳定性与恢复

### 4.1 数据库完整性与备份

数据库是唯一的数据来源，目前没有完整性检查，也没有备份。

**方案**：

- 启动时执行 `PRAGMA quick_check`；
- 每天在维护线程用 `VACUUM INTO` 生成在线备份，保留最近 3 份；
- 检测到损坏时：将原库改名保留、从最近备份恢复、状态栏持续告警。

### 4.2 崩溃诊断与自动重启

- 崩溃时记录现场：Windows 使用 `SetUnhandledExceptionFilter` 写 minidump，Linux 在信号处理中写回溯。
- 启动时检测“上次未正常退出”的标记文件，写日志并在状态栏提示。
- 部署层面提供守护配置：Linux systemd 单元（`Restart=always`），Windows 计划任务。

### 4.3 定时任务不受系统时钟变化影响

每日清理与每周周报使用“长时间单次 `QTimer`”，系统改时间、休眠唤醒或 NTP 校时后会错过或提前执行；程序关闭期间错过的任务也不会补跑。

**方案**：改为每分钟检查一次，对比墙上时间与 `system_config` 中记录的“上次执行日期”。

### 4.4 模型对象的释放

`ImageListModel` 在更新时直接 `delete` 旧的 `ImageItemObject`，QML 中的绑定可能仍持有它们。

**方案**：改为 `deleteLater()`。

### 4.5 长时间运行测试

把本轮使用的端到端脚本整理成 `scripts/simulator.py`：按产线节奏模拟 12 路 FTP 上传与 TCP 报文，可注入异常数据（错误时间、带路径的图片名、断线、半开连接等）。

**验收**：模拟器连续运行 72 小时，期间进程内存、线程数、文件句柄数稳定，数据库与图像目录大小在保留策略下趋于平稳，无未处理错误。

## 附录 A：执行记录与实测（2026-10-20）

### 阶段 A

- **1.1 清理停滞**：清理改为按实际路径 `image_path`（为空时按 `imagename`）分组；路径不安全的组只删记录、保留文件，并在日志与状态栏统计。原复现用例（500 组不安全路径 + 1 条正常记录）现在第 1 轮即清理完成。
- **1.2 磁盘保护**：新增 `common/StorageMonitor`，每分钟检查图像目录、FTP 根目录、数据库与日志所在分区。低于 10% 告警；低于 5% FTP 返回 `452` 并触发紧急清理（逐步缩短保留期，最少保留 7 天，空间无法恢复时至少间隔 10 分钟再试）；低于 2% TCP 也拒收。阈值见 README“可调配置”。
- **1.3 实际路径关联**：`record` 新增 `image_path` 列与索引（在线 `ALTER TABLE`，50 万条记录迁移 169 ms）。FTP 上传回调携带客户端请求的文件名，待关联缓存按请求名建键。端到端验证：图片先到、TCP 先到、`_v2` 重传、`imageName` 带路径四种场景均关联到正确的文件。
  - 修正过程中发现：`_v2` 新图到达时曾把界面上同名的上一批次卡片换成新图。现在只有数据库里确有等待该图的记录时才更新卡片，否则进入缓存。
- **1.4 时间戳**：拒收晚于服务器时间 10 分钟或早于保留天数的报文，错误信息中提示检查客户端时钟。
- **D3 孤儿图片**：每次清理后删除超过保留期 7 天、且没有任何记录引用（按路径或文件名）的图片，每次最多 5000 张。

### 阶段 B

- **2.1 / 2.2**：4 处缩略图与预览设置 `sourceSize`；`ZoomOverlay` 大图关闭共享缓存；统计详情页改为请求 200 条并显示“共 N 张，显示最新 200 张”。
- **2.3**：`gearSumQuery` 移到统计线程（`StatsService::gearSum`）；周报移到维护线程。
- **2.4 清理与入库争用写锁**：50 万条记录测试库上，一批 500 组：选择阶段 141 ms（只读，WAL 下不阻塞写入），删除阶段持有写锁 8 ms。另发现清理队列逐条自动提交（500 次写锁与刷盘），改为单事务后每批由 670 ms 降到 150 ms。无需缩小批大小。
- **2.5 日志**：`ftp.log` 改为常驻打开、节流刷盘；删除界面未使用、每条消息搬移约 200 KB 内存的日志字符串缓冲；删除每次启动 FTP 时在主线程列出整个图像目录的代码；去掉 TCP 日志的重复转发；日志级别可配置（`log/level`，发布版默认 `info`）。

### 阶段 C

- **3.1 TCP**：5 分钟空闲超时与 keepalive；单行上限 64 KB；日志中原始报文截断到 256 字节；未读取的回包超过 1 MB 断开；处理已处理数据一次性移除，避免逐行搬移。
- **3.2 / 3.3 FTP**：按来源 IP 10 分钟失败 10 次封禁 15 分钟，封禁时断开该来源的现有会话；可选来源 IP 白名单（FTP 与 TCP，默认关闭）；被动端口限定在 50000～50100。
  - 测试中发现：拒绝连接时在写出 `421` 后立即 `deleteLater`，拒绝原因可能来不及发出；FTP 与 TCP 的拒绝路径均改为先刷出再在断开后删除。
- **3.4**：数据库打不开或建表失败时显示错误窗口（含原因与日志目录）；FTP / TCP 启动失败每 30 秒自动重试，用户手动停止的不重试。
- **3.5 图片完整性**：实测完整解码并不能发现截断：Qt 的 JPEG 与 BMP 解码器会容忍截断数据（截掉 1/3 的文件仍被接受），且 500 万像素图片每张耗时约 55 ms，在 FTP 线程中串行处理 12 路相机需约 0.65 秒。改为结构完整性检查：JPEG 检查结束标记 `FFD9`（允许尾部补零）、PNG 检查 `IEND` 块、BMP 检查声明长度，其他格式完整解码。三种格式的截断均能识别，耗时 < 1 ms。
- **3.6**：状态栏告警时间改为完整时间。

### 阶段 D

- **4.1 数据库**：新增 `data/DatabaseGuard`。50 万条记录（158 MB）实测：`quick_check` 2.0 秒，`VACUUM INTO` 0.3 秒。因此不在每次启动时检查，只在上次异常退出（运行标记仍在）或日常检查发现损坏时检查；损坏时改名保留原库并从最近一份通过检查的备份恢复。每天随清理时段检查并备份，保留 3 份，存储不足时跳过备份。
- **4.2 崩溃诊断与自动重启**：新增 `common/CrashHandler`。Linux 实测：崩溃后 `crash.log` 记录信号与调用栈（含函数名），进程仍以默认方式终止并生成 core；发布版经 `strip` 后动态符号仍保留。Windows 写 minidump（未在本地编译验证，需 Windows CI）。新增 `packaging/linux/carriervision.service` 与 `packaging/windows/CarrierVision_watchdog.bat`，部署脚本已复制到发布包。

- **4.5 模拟器**：新增 `scripts/simulator.py`。本地缩短版长跑（Debug 构建、offscreen、30 分钟、每 2 秒一架载具、5% 注入异常）：900 架载具、10800 次 FTP 上传、900 条 TCP 报文，非预期结果 0；进程内存 351 MB → 359 MB（第 8 分钟后保持不变），线程 15 → 15，文件句柄 33～37 之间波动；日志中的错误全部来自注入的异常数据。72 小时长跑需在目标机器上以发布版执行。
